## 4.1. Концепция исследования и формализация гипотезы

Главная цель настоящего раздела — экспериментально проверить гипотезу о синергетическом эффекте совместного применения Dynamical Decoupling (DD) и Zero-Noise Extrapolation (ZNE) для 3-кубитного алгоритма Гровера (k = 1, целевое состояние |111⟩), а также построить адаптивное правило выбора одной из четырёх стратегий: BARE, DD, ZNE, ZNE+DD.

Для количественной проверки гипотезы выделены три физико-алгоритмических индикатора:

1. **Показатель дефазировки** \(\mathrm{ratio} = T_2 / (2 T_1)\). При \(\mathrm{ratio} < 0{,}5\) фазовый шум доминирует над релаксацией — DD потенциально полезен.
2. **Алгоритмический ресурс когерентности** \(R_{\mathrm{coh}} = T_2 / T_{\mathrm{circ}}\). Малое \(R_{\mathrm{coh}}\) означает, что длительность схемы сопоставима со временем когерентности — ZNE потенциально полезен.
3. **Окна простоя** \(\mathrm{idle\_ns}\) в расписании ALAP — физическая возможность вставить импульсы CPMG2.

Измерение и решение **разведены**. На каждой точке (бэкенд + тройка кубитов) безусловно измеряются все четыре стратегии; эмпирический оптимум (oracle) — стратегия с максимальной вероятностью успеха \(P(|111\rangle)\). Решающее правило — тонкая функция признаков; пороги \(\mathrm{ratio}^*\) и \(R_{\mathrm{coh}}^*\) подбираются по собранной таблице минимизацией среднего regret (потери вероятности относительно oracle), а не зашиваются вручную.

Физически мотивированное дерево решений:

- \(\mathrm{ratio} < \mathrm{ratio}^*\) и \(\mathrm{idle\_ns} > 0\) → DD-кандидат;
- \(R_{\mathrm{coh}} < R_{\mathrm{coh}}^*\) (или устаревшая калибровка) → ZNE-кандидат;
- оба условия → **ZNE+DD**;
- только DD → **DD**; только ZNE → **ZNE**; иначе → **BARE**.

## 4.2. Аппаратная адаптация и инженерные ограничения

Практическая реализация на процессорах IBM Heron (ibm_fez, ibm_kingston, ibm_marrakesh) потребовала устранения двух критических ограничений пайплайна:

**1. Сбой адресации layout после PadDD.**  
После ALAP/PadDynamicalDecoupling объект `layout` схемы обнулялся. Функция измерения без сохранённых физических индексов считывала кубиты 0–1–2 вместо целевой тройки (например, 22–23–24). На таких точках \(P(|111\rangle)\) падала до 0,0 % при том, что сырые counts были почти полностью в состоянии |000⟩. Исправление: физические индексы фиксируются **до** scheduling и явно передаются в этап измерения.

**2. Топологический контроль.**  
На всех трёх чипах тройка 14–15–16 **не связна** в coupling map. Транспилятор вставлял цепочки SWAP; \(\mathrm{idle\_ns}\) вырастало до 3300–3900 нс (≈ 7–8× относительно связных троек с idle ≈ 460–530 нс). Состояние полностью деградировало: все четыре стратегии давали 0,0 %. В раунде 2 такие тройки исключены предварительным фильтром связности; для обучения политики они остаются в датасете как «мёртвые» точки с oracle = BARE (по умолчанию при равенстве нулей).

## 4.3. Состав экспериментального датасета и валидация

### Состав датасета (N = 47)

| Источник | Число точек | Описание |
|---|---:|---|
| Симуляционная сетка (`generic_backend_3q`) | 27 | Aer + thermal relaxation + когерентное дефазирование 0,3 rad/µs |
| Fake-бэкенды | 3 | FakeBrisbane, FakeKyoto, FakeSherbrooke |
| Реальное железо IBM Heron | **17** | ibm_fez (6), ibm_marrakesh (6), ibm_kingston (5) |
| **Итого** | **47** | |

Железо собрано в два раунда:

- **Раунд 1 (6 точек):** тройки 0–1–2 и 14–15–16 на fez / kingston / marrakesh.
- **Раунд 2 (11 точек):** только **связные** тройки на границах \(\mathrm{ratio}\) и \(R_{\mathrm{coh}}\) (после фикса layout).

### Распределение oracle (argmax по четырём стратегиям)

**Весь датасет (N = 47):**

| Класс | Число | Доля |
|---|---:|---:|
| ZNE+DD | 35 | 74,5 % |
| ZNE | 9 | 19,1 % |
| BARE | 3 | 6,4 % |
| DD | 0 | 0 % |

**Только реальное железо (N = 17):** ZNE+DD — 8, ZNE — 6, BARE — 3 (все три — мёртвые 14–15–16). Чистый DD ни разу не был oracle на железе: при коротком idle (~500 нс) DD часто даёт нулевой/отрицательный прирост, а выигрыш уходит в ZNE или в комбинацию ZNE+DD.

### Ключевой эмпирический результат (синергия)

На **ibm_fez**, тройка **0–1–2** (\(\mathrm{ratio} \approx 0{,}41\), \(R_{\mathrm{coh}} \approx 62\), idle ≈ 460 нс):

| Раунд | BARE | DD | ZNE | **ZNE+DD** |
|---|---:|---:|---:|---:|
| 1 | 19,2 % | 35,8 % | 22,1 % | **48,0 %** |
| 2 (повтор) | 29,6 % | 39,1 % | 38,8 % | **52,3 %** |

По отдельности методы дают умеренный прирост; вместе — более чем двукратный рост относительно BARE. Это согласуется с картиной: DD переводит медленный (1/f) фазовый шум в более «белый», после чего Richardson-ZNE корректно экстраполирует остаточную ошибку.

Контраст — короткие окна на kingston/marrakesh (idle ≈ 500–520 нс): часто oracle = **ZNE**, а чистый DD почти не помогает (накладные X-импульсы CPMG2 без достаточного окна дефазировки).

### Подгонка порогов и оценка

Пороги подбирались **grid search** по таблице (минимизация mean regret). Обобщающая способность оценивалась **5-fold cross-validation** (на каждом фолде пороги заново подбираются на 37–38 точках, тест — на 9–10). Для сравнения приведён также одиночный train/test split 50/50.

**Подогнанные пороги на полном датасете (N = 47):**

\[
\mathrm{ratio}^* = 0{,}60,\qquad R_{\mathrm{coh}}^* = 70,\qquad \mathrm{idle\_min} = 0~\mathrm{нс}.
\]

#### Сравнение с бейзлайнами

Поскольку oracle в 74,5 % случаев — **ZNE+DD**, наивный бейзлайн «всегда ZNE+DD» даёт высокую accuracy. Сравнение **честное**: метрика проекта — не только accuracy, но и **mean regret** (средняя потеря \(P(|111\rangle)\) относительно oracle).

| Метод | Accuracy | Mean regret |
|---|---:|---:|
| Всегда BARE | 6 % | 11,7 п.п. |
| **Majority-class (всегда ZNE+DD)** | **74,5 %** | **0,20 п.п.** |
| Адаптивная политика (in-sample, N=47) | 72 % | 0,39 п.п. |
| **5-fold CV (адаптивная)** | **72,4 % ± 16,7 %** | **0,40 ± 0,23 п.п.** |
| Train/test 50/50, test | 62 % | 2,15 п.п. |

**Интерпретация для защиты:**

1. **Accuracy ниже majority на 2,5 п.п.** — ожидаемо при перекошенном oracle (35/47 = ZNE+DD). Это не провал модели, а следствие дисбаланса классов.
2. **Regret остаётся субпроцентным** (0,39–0,40 п.п.): даже когда политика ошибается, промах почти всегда между близкими **ZNE** и **ZNE+DD**, а не между BARE и оптимумом.
3. **Ценность адаптивного правила** — не «обогнать majority по accuracy», а **не запускать тяжёлую ZNE+DD там, где достаточно ZNE** (короткий idle на kingston/marrakesh), при этом сохраняя regret на уровне долей процента.
4. **5-fold CV** устойчивее одного случайного split (test 62 % / 2,15 п.п. — один неудачный разбиение); средний regret по фолдам **0,40 п.п.** согласуется с in-sample.

#### Разбивка по подвыборкам (адаптивная политика, in-sample)

| Выборка | Accuracy | Mean regret |
|---|---:|---:|
| Весь датасет (N = 47) | 72 % | 0,39 п.п. |
| Только sim + Fake (N = 30) | 90 % | 0,05 п.п. |
| Только IBM Heron (N = 17) | 41 % | 0,99 п.п. |
| Majority на Heron (всегда ZNE+DD) | 47 % | 0,46 п.п. |
| 5-fold CV на Heron (N = 17) | 42 % ± 26 % | 1,05 ± 0,77 п.п. |
| Живые точки Heron без 14–15–16 (N = 14) | 50 % | 1,20 п.п. |

На железе точность классификации ниже, чем на симуляторе: типичный промах — **ZNE vs ZNE+DD**. Глобальный порог по `idle_ns` alone не отделяет «полезный DD на fez при 460 нс» от «бесполезного DD на kingston при 500 нс» — ограничение текущей модели.

Эволюция порогов по мере добавления железа:

| Датасет | \(\mathrm{ratio}^*\) | \(R_{\mathrm{coh}}^*\) | Acc. | Regret |
|---|---|---|---:|---:|
| sim + Fake | 0,50 | 35 | ~90 % | ~0,05 п.п. |
| + раунд 1 | 0,50 | **65** | 78 % | 0,14 п.п. |
| + раунд 2 (финал) | **0,60** | **70** | 72 % | 0,39 п.п. |

Рост \(R_{\mathrm{coh}}^*\) отражает, что реальное железо «шумнее» GenericBackendV2: ZNE нужен уже при более высоком запасе когерентности (как на fez при \(R_{\mathrm{coh}} \approx 62\)).

## 4.4. Методологический вывод

Результаты согласуются с гипотезой синергии DD+ZNE, но **не подтверждают её безусловно**:

1. На ibm_fez (0–1–2) гибрид устойчиво лучший в двух независимых прогонах.
2. На коротком idle доминирует ZNE; DD может не давать прироста.
3. Несвязная топология полностью убивает сигнал — это не провал mitigation, а инженерный фильтр.
4. Правило \(\mathrm{ratio}^*{=}0{,}60\), \(R_{\mathrm{coh}}^*{=}70\) хорошо работает на смешанном датасете (regret 0,39 п.п.), но на одних только 17 реальных точках accuracy скромная — нужна большая выборка и, вероятно, взаимодействие \(\mathrm{ratio}\times\mathrm{idle}\).

Ограничения: смешение sim/Fake и real при обучении; упрощённая модель delay в симуляторе; k = 1; малый N на железе (17).

## Заключение (замена финальных абзацев)

В работе выдвинута и проверена гипотеза о синергетическом эффекте совместного применения DD и ZNE для алгоритма Гровера на NISQ-процессорах.

**Этап 1 (раздел 3).** Модельная задача: 3-кубитный Гровер (k = 1) на Fake/шумных бэкендах Kyoto и Sherbrooke. На Sherbrooke гибрид DD+ZNE дал заметный прирост относительно BARE; на сильно зашумлённом Kyoto синергия в приросте точности не проявилась, но стабилизировала результат.

**Этап 2 (раздел 4).** Измерительный стенд на реальном IBM Heron (fez, kingston, marrakesh) и симуляционной сетке. Сформирован датасет **N = 47** (27 sim + 3 Fake + **17** реальных точек). Исправлены layout-баг и учтён SWAP-коллапс несвязных троек. Подобраны пороги \(\mathrm{ratio}^* = 0{,}60\), \(R_{\mathrm{coh}}^* = 70\): in-sample accuracy 72 %, mean regret 0,39 п.п.; на отложенном test — accuracy 62 %.

Главный эмпирический якорь синергии — **ibm_fez, кубиты 0–1–2**: BARE 19 % → ZNE+DD **48 %** (раунд 1) и 30 % → **52 %** (раунд 2).

Итоговый вывод формулируется осторожно: данные **согласуются** с гипотезой синергии DD и ZNE; эффект **гранично-зависим** (особенно от idle и топологии) и оценён на ограниченной железной выборке. Дальнейшая работа: больше связных троек на Heron, порог/взаимодействие по idle, переобучение только на real.

## Итоговое решающее правило (для вставки в текст / рисунок)

```
if ratio < 0.60 and idle_ns > 0:
    need_dd = True
if R_coh < 70:
    need_zne = True

if need_dd and need_zne:  return ZNE+DD
if need_dd:               return DD
if need_zne:              return ZNE
else:                     return BARE
```
